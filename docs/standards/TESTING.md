# Testing

`scripts/check.sh` runs the same checks locally and in CI. A pull request cannot merge
until it passes.

## What each layer tests

| layer | tests | data needed |
|---|---|---|
| `qvp-format`, `qvp-core` | unit tests on synthesised pages | none |
| `qvp-convert` | the identity gate: SVG → QVP → SVG, rasterised at 4×, pixel-diffed. 8 pages on every PR, all 604 nightly | the `quran-svg-elements` bundle (`pages/`, `index/`) |
| `qvp-ffi` | one ABI test per function family on a real page | the data release (`dist/pages/`) |
| each wrapper | one binding test per C symbol on a known page, plus the shared scenarios | the data release |
| each example | one UI smoke test: open a page, tap a word, highlight. The iOS Demo has it, as `DemoUITests`, and the iOS workflow runs it on the simulator. The web example has it as `web/example/smoke.test.mjs`, which Chromium runs through Playwright in the `web example` job. The Flutter example has it as `example/test/smoke_test.dart`, a widget test on the host engine library that the Flutter workflow runs. The React Native example has it as `__tests__/smoke.test.tsx`, a Jest test that sends the native view's page-load and word-tap events and checks the `highlights` prop the app sends back. Jest has no device, so the engine does not draw it there. The Android `device` job runs the Kotlin library's tests, and the Android example has no smoke test yet | the example's page set. The web test serves `dist/pages` |
| `web/lite.mjs` | the conformance fixtures | `conformance/` |
| `web/lite-passage.mjs` | synthetic ranges, unchanged paths, markers, bounds, cross-page ranges, Rust ink metrics and the core's passage scenarios | synthetic tests need no data; the 604-page sweep and the scenarios require `dist/pages/` in `gates` |

Without their data, the data tests skip locally and print a hint. In CI they fail instead
(`QVP_REQUIRE_DATA=1`), because `scripts/sync-test-data.sh` provides the data there: the
page data release of this repository and the `quran-svg-elements` release (the source SVG
bundle, with `pages/` and `index/`).

## Cross-wrapper scenarios

`conformance/scenarios/*.json` are golden outputs generated by the Rust core
(`scripts/gen-conformance.sh`) for fixed inputs: page 042 at ten viewport sizes in every
fit mode, hit tests at fixed points, a search, a highlight's boxes. Every wrapper's test
suite runs the same scenarios through its public API and compares the numbers. A wrapper
that reimplements a formula fails with the exact divergence. When a computation moves from a
wrapper into the core, it gets a scenario.

## What a change must ship with

- A new engine function: a core unit test, an ABI test call, a binding test in each
  wrapper, and its row in the parity table. The parity script checks that the binding test
  files name the symbol.
- A bug fix: a test at the lowest layer that reproduces it, failing before and passing
  after.
- A platform convenience: a test in that platform's suite.

## What CI runs

Each job runs one `scripts/check.sh` command, named in the last column. A PR that changes
only documents skips `engine`, `gates`, `web` and `web example`, and a skipped job counts as passing.

| job | runs on | contents | `scripts/check.sh` |
|---|---|---|---|
| `engine (fmt, clippy, tests, rustdoc)` | PRs that change code | format check, clippy with warnings as errors, workspace tests, rustdoc, the prose report | `fmt lint test docs` |
| `gates (identity, ABI, conformance)` | PRs that change code | identity gate (8 pages), line shift, zoom control, passage and ABI tests, conformance fixtures, zoom table, then the web tests that read pages with `QVP_REQUIRE_DATA=1`: `smoke.mjs`, `lite-passage.test.mjs`, `scenarios.test.mjs`, `passage.test.mjs` | `gates` |
| `standards (parity, versions, terminology, structure)` | every PR | parity (`--check`), versions, structure, terminology (zero findings), shellcheck over every shell script, and the eslint doc-block check. The job has no Flutter, so `parity` skips the Flutter bindings check, and no swiftlint, so `docblocks` skips it | `parity versions structure terminology shell docblocks` |
| `web (wasm, smoke, lite)` | PRs that change code | wasm build, then without data: `smoke.mjs`, `lite.test.mjs`, `lite-passage.test.mjs`, and a parse of the web example | `web` |
| `web example (UI smoke test)` | PRs that change code | Playwright and Chromium, then the web example's UI smoke test with `QVP_REQUIRE_DATA=1`. Not a required check | `example` |
| `android`, `ios`, `flutter`, `react-native` | PRs that touch that package or its workflow. `android`, `ios` and `flutter` also run for `crates/` and the Cargo manifests; `android`, `flutter` and `react-native` also run for the shared Android toolchain action; `react-native` also runs for the Kotlin library; `flutter` also runs for `scripts/build-engine-ios.sh` and `scripts/build-engine-windows.ps1` | build and the package's tests. `flutter` also runs the example's smoke test and checks that the generated `bindings.dart` matches the header (`scripts/check-flutter-bindings.sh`). Its four jobs are below the table. `android` runs detekt, and `ios` runs swiftlint in a Linux job of its own, the doc-block checks of `CODE-STYLE.md` | none; each workflow lists its commands |
| `nightly` | schedule | identity gate over all 604 pages, and the benchmark on page 042 uploaded as an artifact for comparison with `docs/MEASURED.md` | none |

The `flutter` workflow has four jobs:

- `test` (Linux) runs the `dart:ffi` suite and the example's smoke test. Then it runs the
  shared public-API cases on the web backend in Chrome.
- `example` (Linux) builds the example for Android and web.
- `darwin` (macOS) runs the `dart:ffi` suite on the dylib. Then it builds the example for
  macOS and the iOS simulator, once with Swift Package Manager and once with CocoaPods.
  `scripts/check-darwin-engine-symbols.sh` checks that each app exports the engine.
- `windows` builds the example for Windows and checks that the app bundles `qvp_ffi.dll`.

Locally, `scripts/check.sh` with no argument runs every command above once. `web` then
leaves `smoke.mjs` and `lite-passage.test.mjs` to `gates`, which runs them with data.
`example` skips its test when Playwright is not installed in `web/example`.

## How it is checked

The branch ruleset of `main` requires the names of the `engine`, `gates`, `standards` and
`web` jobs in the table above as status checks, by exact string. A rename of one of them
needs the ruleset updated first, or no PR can merge. Every platform job that ran must pass as well.
